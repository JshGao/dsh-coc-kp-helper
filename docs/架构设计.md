# COC 守秘人备团 Agent Preset —— 架构设计

> 状态：**已定案，待实施**。
> 本文档替代此前的评审稿，是实施依据：结论、规范、目录、脚本、流程、验收全部固定。
> 开发工作目录 `dsh-coc-kp-helper/` 只用于开发与测试（含 `fixtures/`、`vault-test/`）；真正使用时，守秘人另开一个**以自己 Obsidian 仓库为工作目录**的会话。

---

## 1. 目标与定位

把一本 COC 模组（pdf / docx / doc / txt / md / rtf / html）转成守秘人跑团时可当场翻用的 Obsidian 笔记树：场景笔记（环境描写 + 可互动线索 callout）、NPC 笔记（身份与外貌 + 按场景的问答）、以及空置的素材与调查员文件夹。

**设计立场**：v1 不做法官、不核规则、不做跑团现场模式。唯一追求是**场景与 NPC 反应写得合理、可读、可直接照着念**。

**成功标准**（可机械验收）：

1. 输出树与 §5 完全一致；原始模组文件保持原样未被改写。
2. 场景笔记 frontmatter 属性齐全且顺序为 `tags / date / 地点 / 天气 / 人物`；`tags` 四项顺序为 `TRPG / COC / <模组名> / 场景`。
3. 每条 callout 均有空格（`> [!success] …`），标题含"成功/失败"字样；`[!fail]` 只在"失败会产生特别事件"时出现。
4. NPC 笔记 frontmatter 仅含 `tags`（`TRPG / COC / <模组名> / NPC`）；正文以分点写身份与外貌，随后按场景分组列出问答。
5. `lint_notes.py` 零 fatal；覆盖检查（场景清单 vs 实际文件）无缺口。
6. `standingKeyFor('coc-kp')` 挂载校验通过。

## 2. 地基事实（实测，决定了架构边界）

| # | 事实 | 依据 | 架构后果 |
|---|---|---|---|
| F1 | 沙箱可写根 = 宿主启动时的 `process.cwd()`，**会话级不可改** | `dsh-base/cordis.patch.yml:205-212`；本机实测写工作区外被拒 | "vault 成为工作目录" = **以 vault 为 cwd 启动会话**。守秘人每次备团按模组文件夹开会话，天然够用 |
| F2 | 提权是会话级整体放开（`danger-full-access → approval: never`），不是逐条批准 | `permission-presets` | 不需要提权；也不要用它 |
| F3 | 读不受限，只有写受沙箱限制 | 实测：`read` 可读工作区外的 `~/.dsh/settings.yaml` | 扫描仓库、lint、汇报永远不需要提权 |
| F4 | **子 agent 无法申请审批**，越界操作被自动拒绝且不得重试 | `dsh-subagent` 的 `SUBAGENT_DELEGATION_CONTEXT` | 所有落盘必须在父已具备权限的目录内 —— 与 F1 的"工作目录=vault"完美契合 |
| F5 | 子 agent 继承父的 `cwd` 与 preset | `childSessionMeta()` | 子 agent 与父共享系统提示与工具表，前缀缓存可复用 |
| F6 | 缓存是 provider 端自动前缀缓存，harness 只统计 `cacheReadTokens/cacheWriteTokens` | `dsh-llm` 类型定义 | 工具表/提示段一旦中途变化，从该点起缓存全废 → 禁止轮内动态改工具与提示 |
| F7 | web 部署已把宿主层 `tool-web / tool-fs / tool-bash / skill-filesystem / tool-subagent / tool-workflow / agent-instructions / tool-todo` 全部禁用，改由 preset 贡献 | `dsh-web-app/cordis.patch.yml:360-484` | preset 里这些行是**唯一来源**；漏掉哪行，能力就真的不存在 |
| F8 | `/usr/bin/textutil` 零依赖处理 docx/doc/rtf/html，中文正确 | 实测（自造中文 docx → 正确输出） | Word 系不必进 Python |
| F9 | PDF 抽取需装依赖但可行；`pip` 默认缓存目录不可写 | 实测 `/usr/bin/python3`(3.9.6) + `venv` + `pypdf` 抽出真实 PDF 文本，伴随可写警告 | 抽取走"仓库内 `.venv`"，`pip install --no-cache-dir` |
| F10 | 技能可携带 `references/`、`scripts/`，按绝对路径调用即可 | `skill-filesystem` 只扫 `<name>/SKILL.md`；bundle 在可读的 `~/.dsh/.agent-presets/` 下 | 脚本用 `python3 /预设路径/scripts/x.py`，无需部署目录可写 |
| F11 | 上传的文件在提示词里被投影为"名字 + 字节数 + 只读绝对路径" | `dsh-llm` 的 `FileBlock` 契约 | 聊天里丢文件后，父能拿到路径；但**把文件搬进仓库仍需仓库可写**（= F1 已满足） |

## 3. 三层架构总览

```
┌────────────────────────────────────────────────────────────────────┐
│ 层 1  能力（preset 组合）   ~/.dsh/.agent-presets/coc-kp/agent.cordis.yml │
│        persona（守秘人备团身份）+ skill-filesystem（技能发现）        │
│        其余行照抄 standard（工具表与 context 管理）                   │
└────────────────────────────────────────────────────────────────────┘
                                │ 提供
┌────────────────────────────────────────────────────────────────────┐
│ 层 2  知识（技能包）  skills/coc-kp-prep/                            │
│        SKILL.md（父的 SOP，≤120 行）                                 │
│        references/  obsidian-conventions · scene-authoring ·         │
│                     npc-authoring · pipeline                          │
│        scripts/     extract_module.py · lint_notes.py                 │
└────────────────────────────────────────────────────────────────────┘
                                │ 写在
┌────────────────────────────────────────────────────────────────────┐
│ 层 3  内容（仓库产物）  <模组名>/                                     │
│        总览.md · 场景/*.md · 角色与势力/{NPC,调查员}/ · 素材/ · .meta/ │
└────────────────────────────────────────────────────────────────────┘
```

**分工原则**：层 1 只管"它是谁、它能用什么"；层 2 管"怎么做、长什么样"（跨运行稳定、可演化）；层 3 管"这本书的事实"（模组概要、专名表、进度、成果）。

**明确不做**：不新增任何 Cordis 服务 → **preset 内不需要 `isolate` realm**；不碰宿主组合。

## 4. Preset 组合（层 1）

### 4.1 目录与元数据

```
~/.dsh/.agent-presets/coc-kp/
├── agent.cordis.yml
├── preset.yml
└── skills/coc-kp-prep/{SKILL.md, references/*.md, scripts/*.py}
```

`preset.yml`：

```yaml
name: COC 守秘人备团模式
description: 把 COC 模组转化为 Obsidian 备团资料：场景笔记、NPC 问答、总览索引。不核规则、不做现场裁判。
```

### 4.2 组合内容（从 `standard` 复制后改动的行）

| 行 | 处理 | 说明 |
|---|---|---|
| `persona` | **改写** | 见 §4.3 |
| `agent-instructions` | 删除 | 备团不需要仓库内 `AGENTS.md` 注入（减少每轮常驻）；风格约定走 §8.6 |
| `tool-subagent` / `tool-subagent-fork` / `tool-subagent-control` / `tool-subagent-list-agents` | 删除 | 子 agent 策略保留但工具不在位：跨会话续跑用 goal，子任务用 `workflow`；少四行常驻工具表，前缀更小 |
| `tool-workflow` + `workflow-worker-thread` | 保留 | 场景 fan-out 的编排工具（§7.2 裁决表用它） |
| `tool-ralph` | 删除 | 与备团无关 |
| `tool-jobs` | 删除 | 后果：`tool-bash` 的 `run_in_background` 不可用，长抽取改为前台等待（见 §10 E13） |
| `tool-bash` / `tool-pwsh` | 保留 | 抽取与脚本调用的载体 |
| `tool-fs` / `tool-fs-search` | 保留 | 写笔记；`sampleOverCapGlobResults: false` 照抄 |
| `skill-filesystem` | **改 config** | `customSkillDirs: [!!js fileURLToPath(new URL('skills/', baseUrl))]`，与 shipped `cordis` preset 同写法 |
| `tool-skill` | 保留 | 技能的目录与加载入口 |
| `command-goal` / `tool-goal` | 保留 | 长流程（整本模组）跨轮续跑的载体 |
| `planning`（plan-mode 组） | 保留 | 计划模式；realm 与 standard 一致 |
| `compaction`（组） | 保留，**调参** | `thresholdChars: 6144`、`headChars: 3072`、`tailChars: 1024`（场景笔记是大产物） |
| `tool-ask-user` | 保留 | 备团开始时的必要澄清（模组路径、专名读法） |
| `tool-todo` | 保留 | 进度可视化 |
| `tool-web` | 保留 | 查年代细节/专名译法（可选联网核证） |
| `present` | 保留 | 交付物挂出 |

> **realm 规则的核对**：`planning` 与 `compaction` 两组在 standard 里就带 `isolate`，照抄即可；本 preset 不新增任何"发布服务"的行，因此没有新的 realm 需要声明（`delegation` 组的 `workflowEngine` realm 也随之保留，因为 `tool-workflow` 仍在位）。若实施时给某行加了服务，`standingKeyFor` 会以 `row(s) published process-global service(s) [...]` 明确拒绝——那时才需要包 `isolate`。

### 4.3 persona（中文，写死三件事）

要点（正式文案在实施时定稿，长度控制在 12~18 行）：

1. **身份**：你是 COC 7th 守秘人（KP）的备团助手；你的产出是 Obsidian 笔记，不是对话式回答。
2. **工作目录 = 用户仓库**：所有产出写在当前工作目录内；先确认工作目录可写再动手。
3. **不问就跑**只在两件事上问：模组文件的**确切路径**、以及无法从模组判断的**专名读法/译名**。
4. **基调纪律**：COC 的恐怖来自"常态被撕开一角"，不是处处阴暗压抑。场景可以是明亮、热闹、温暖的；恐怖靠"不对劲的细节"和你留给守秘人的伏笔，不靠堆形容词。
5. **不核规则**：不裁定技能难度、不给骰点建议、不写数值平衡；只写"会发生什么"与"守秘人怎么演"。
6. **边界**：不修改用户原始模组文件；不覆盖用户已手改的笔记；`素材/` 与 `调查员/` 只创建不填内容。
7. 加载 `coc-kp-prep` 技能后再开工（技能里是规范与 SOP）。

## 5. 仓库结构与产物规格（层 3）

### 5.1 目录树

```
<仓库根>/
├── <模组名>.pdf                      ← 用户导入的原始模组（只读，永不改写）
├── <模组名>/
│   ├── 总览.md                       ← 索引：场景清单、NPC 清单、进度、未决问题
│   ├── 场景/
│   │   ├── <场景名>.md
│   │   └── …
│   ├── 角色与势力/
│   │   ├── NPC/
│   │   │   └── <NPC名>.md
│   │   └── 调查员/                    ← 只创建（+ `_README.md` 占位说明）
│   ├── 素材/                          ← 只创建（+ `_README.md` 占位说明）
│   └── .meta/
│       ├── source.txt                ← 带页标记的抽取稿（子 agent 只读这个，不读 pdf）
│       ├── outline.md                ← 场景大纲 + 行号窗口 + 出场 NPC
│       ├── glossary.md               ← 专名表（唯一写法）
│       ├── manifest.md               ← 源文件信息、抽取质量、进度、已写文件
│       ├── lint-report.txt           ← lint 输出（机器可读）
│       └── .venv/                    ← 仅在需要 PDF 抽取时创建
```

### 5.2 命名规则（必须机械遵守）

| 对象 | 规则 |
|---|---|
| 模组文件夹名 | `= 原始模组文件的基名`（去掉扩展名），如 `快乐王子.pdf` → `快乐王子/` |
| 笔记基名 | **纯名字，不加序号**（`德莱尼子爵府.md`）。理由：Obsidian 的 `[[名字]]` 按基名解析，加 `01-` 前缀会让"最短路径"设置下解析失败 |
| 场景顺序 | frontmatter 里有 `date` 时按时间排，否则按源文出现顺序；顺序写在 `总览.md`，不写进文件名 |
| tag 中的模组名 | slug 化：空格→`-`，去掉 `#`、`[`、`]`、`/`、`|`，首字符不能是数字 |
| 链接目标 | 一律 `[[基名]]`，与文件名逐字相同 |

### 5.3 场景笔记属性（**以示例为准**）

```yaml
---
tags:
  - TRPG
  - COC
  - "#快乐王子"
  - "#场景"
date: 1891-09-30T10:00:00
地点: 伦敦海德公园附近，德莱尼子爵府邸
天气: 秋雨初歇，薄雾未散，空气中弥漫着潮湿的寒意
人物:
  - "[[埃尔文·琼斯]]"
  - "[[大卫·霍华德]]"
  - "[[玛丽]]"
---
```

硬规则：

1. 属性**顺序固定**：`tags → date → 地点 → 天气 → 人物`。
2. `tags` 四项**顺序固定**：`TRPG`、`COC`、`"#<模组名>"`、`"#场景"`；写为 2 空格缩进的块序列。
3. `date` 用 `YYYY-MM-DDTHH:MM:SS`（模组给不出精确时间时，用模组给出的日期 + 合理解析的时段；确实无日期则**省略该属性**）。
4. `地点` 是**自由文本**（可含逗号、修饰语），不加 wikilink。
5. `天气` 一句话，暗示氛围但不越界（例：`秋雨初歇，薄雾未散，空气中弥漫着潮湿的寒意`）。模组未描述时，写与该场景基调一致的合理天气，**不得引入新设定**。
6. `人物` 是 `[[NPC名]]` 列表，只列**该场景实际出场**的 NPC（有台词的、或调查员可能交谈的），且每个都必须有对应 NPC 笔记。

### 5.4 场景笔记正文结构

自由度与硬约束并存：**地点/房间为主干标题，互动与分支为子标题，callout 挂在互动点之后**。

```
## <地点/房间 A>              ← 调查员会走进的第一个空间
<环境描写：调查员视角，可逐段推进>
### <此处的互动物 / 次空间>
> [!success] <技能>成功
> <结果叙述>
> [!fail] <技能>失败            ← 仅当失败有特别事件
> <失败后的特别结果>
## <地点/房间 B>
…
### <分支：调查员可能的选择>
<该分支下 NPC 的反应 / 事件>
```

硬规则：

1. **标题层级**：`##` 用于空间/地点，`###` 用于该空间内的互动物、证言、分支。不出现 `#` 一级标题（笔记标题即文件名）。
2. **人称与视角**：环境描写用"你们"（调查员视角）。若模组或用户风格偏好第三人称，以用户当次指令为准。
3. **callout 语法必须带空格**：`> [!success] …`、`> [!fail] …`、`> [!tip] …`。
   - 标题格式：`<技能名>成功` / `<技能名>失败`；技能名照模组原文（如"侦查""聆听""估价""会计/伪造""交涉技能极难"）。
   - 免检定或纯氛围提示用 `> [!tip] …`，标题自拟。
   - `[!fail]` 是**例外**，只在"失败本身会产生特别事件"时写，绝不与每个 `[!success]` 成对出现。
   - 多条 callout 连续排列时，块之间空一行。
4. **保留原文的戏剧性信息**：日记、信件、证言等第一手材料**引号原文照录**，不做概括改写。
5. **不写**：时间线区块、战斗数据区块、守秘人备忘区块、检定难度数值裁定（你可写"极难""困难"这类原文里已有的措辞，但不自行发明规则判定）。

> **例外说明**：示例中个别 callout 出现了 `>[!success]`（缺空格）与 `>[!tip] <标题>`（提示而非检定）两种形态。**规范要求一律带空格**；`[!tip]` 用于非检定提示是允许的。

### 5.5 NPC 笔记规格

```yaml
---
tags:
  - TRPG
  - COC
  - 快乐王子
  - NPC
---
- **身份**：伦敦警察局总警督
- **外貌**：四十岁左右，英俊，三件套西装，自信。

## <场景 A 名>
<出场描写：他是怎么出现的、在做什么、对调查员的态度>
### <调查员可能提出的问题 / 触发的局面>
<他的回应，直接引语；态度与潜台词写进去>
#### <追问 / 施压后的分支>        ← 需要时才有
> [!success] <技能>成功
> <他会说什么、做什么>
> [!fail] <技能>失败
> <失败的特别后果>

## <场景 B 名>
…
```

硬规则：

1. frontmatter **只含 `tags`**，顺序 `TRPG / COC / <模组名> / NPC`（`#NPC` 标签按示例不带引号）。
2. 正文开头**两条分点**：`- **身份**：…` 与 `- **外貌**：…`（外貌要能被守秘人直接念给玩家）。
3. `##` = 场景名（与场景笔记同名，便于对照）；`###` = 玩家可能问的话题/处境；`####` = 追问分支。
4. **问答必须来自原文**：NPC 的回应要有模组依据（或据其人设可合理推演），不得凭空发明关键情报。
5. **允许的推演**：玩家"可能问但模组没写"的问题，可在人设一致的范围内补写，并在文中保持语气一致；不得让 NPC 泄露模组指定的隐藏信息。
6. NPC 之间、NPC 与地点之间的交叉引用用普通 `[[链接]]`。
7. **块引用锚点（`^锚点`）与 `![[NPC#^锚点]]` 嵌入：v1 不生成**，列在 §12 的后续增强。

### 5.6 `总览.md`

守秘人现场最常翻的一页，也是父的"外部记忆"：

```markdown
# <模组名> · 备团总览

## 场景
- [[场景笔记基名]] — 一句话用途
## NPC
- [[NPC 名]] — 一句话身份，出场于 [[场景 A]]、[[场景 B]]
## 进度
- [x] 抽取源文 / 大纲 / 场景 12/12 / NPC 5/5 / lint 通过
## 待人工确认
- <页 12 图片页无文字层，未纳入>
## 本模组专名
- 见 [[.meta/glossary]]（Obsidian 中隐藏目录不便链接时，此处直接列表）
```

### 5.7 `.meta/` 各文件

| 文件 | 内容 | 谁写 |
|---|---|---|
| `source.txt` | 抽取稿；每页以 `[[p12]]` 起头，行号由 `read` 工具自然给出；开头一段元信息（源文件、页数、抽取器、质量指标） | `extract_module.py` |
| `outline.md` | 表格：`场景名 \| 源文窗口 [L120-L480] \| 出场 NPC \| 用途一句话` | 父 |
| `glossary.md` | 专名表：`原名 → 唯一写法`（人名/地名/机构/造物），中英混排模组尤其需要 | 父（读源文后定） |

# COC 守秘人备团

## 0. 开工前（必做，不可跳过）
- 确认工作目录可写：写 `.coc-kp-write-test` 再删除；失败则**立即停手**，
  告诉用户两种解法（以仓库为工作目录重开会话 / 该会话显式授予全盘写入），
  **不要反复重试，不要指望子 agent 能获批**（子 agent 的越界操作会被自动拒绝）。
- 拿到模组文件的**确切路径**。用户可能在对话里上传（提示词里会给出只读绝对路径）
  或直接放在仓库里；两种都要先确认文件存在，再复制/落位到仓库根。
- 读 references/obsidian-conventions.md（唯一权威规范），并读 references/pipeline.md。

## 1. 抽取

## 2. 大纲与专名

只读"够用"的部分：不要通读全文（那是子 agent 的活）。

## 3. 场景笔记

**子 agent 的指令必须自包含**：把 references/scene-authoring.md 的要点与
references/obsidian-conventions.md 的硬规则**转述**进 prompt（固定块在前），
本场景的源文窗口放最后（可变块）。子 agent 只允许 write 它自己那一个目标文件。

## 4. NPC 笔记

直接写 NPC 笔记 —— 不要"先写场景再靠场景笔记汇总"（信息会蒸发）。

python3 <技能目录>/scripts/lint_notes.py --module <模组名> --out <模组名>/.meta/lint-report.txt

### 6.3 `references/scene-authoring.md` 要点（方法论）

- **先空间，后事件**：读者（守秘人）是按"玩家进门看到什么"来念的，所以按空间推进，而不是按时间线。
- **一次给一个感官锚点**：光线、气味、声音、温度、脚下的质地，挑 1~2 个具体细节，胜过堆形容词。
- **恐怖靠"不对劲的比例"**：一切正常但有一处细节不对（仆人挤在一起、草坪上的靴印只进不出、宝石内部浑浊）。明亮场景可以有明亮的愉快——不要把所有场景都写成阴天。
- **线索要可操作**：每个 callout 对应"玩家说我要做 X"的瞬间；不要把背景设定当线索写。
- **留白给守秘人**：不确定玩家会不会发现的东西，写成 NPC 笔记里的回应，或写成 `[!tip]` 提示，而不是写进必读的环境描写。
- **引文照录**：日记、信件、证言、原话，逐字保留。

### 6.4 `references/npc-authoring.md` 要点

- **身份+外貌两行**决定守秘人第一次介绍这个人的方式：写得能被直接念出来。
- **按场景分组**，组名用场景笔记名，方便现场对照。
- **每个话题写成"玩家问 → 他答"**；答案是引语，态度与潜台词写在动作里（"他低头看了一眼脚边的宝石，用靴尖拨开"）。
- **区分三种回应**：`直接回答`（他知道且愿说）、`回避/误导`（他知道但不愿说）、`推诿/威胁`（被逼到墙角）。这三种的差别就是这个 NPC 的性格。
- **检定挂钩**：只有模组明确要求检定时才写 callout；标题照原文技能名。
- **绝不泄露**：模组标为"秘密"的信息，只能通过"他慌乱之下说漏嘴""他撒谎被识破"这类**有条件**的路径出现。

### 6.5 `references/pipeline.md` 要点

- 抽取细节、页标记格式、质量指标与阈值。
- 场景切分判据：换空间、换时间、换在场人物、换功能（调查→对峙）。
- fan-out 裁决表（§7.2 的完整版）、批次大小、失败重试与断点续跑。
- lint 输出的解读与修法（哪类问题只改行、哪类要重建文件）。
- 止损规则：不可写、抽取失败、用户手改文件、模组远超预期长度（> ~200k token 源文）时先报告再继续。

## 7. 子 agent 策略（成本与缓存）

### 7.1 原理（写进 `pipeline.md`，避免实施时凭感觉）

用户唯一付费的是 token，而 token 分两种命运：**缓存读**（便宜，前缀未变的部分）与**未缓存输入 + 输出**（贵）。

由此得出一个反直觉但正确的结论：

> **用子 agent 天然是缓存不友好的。** 每个子 agent 都是一条全新对话，没有父的历史，前缀从第一个 token 重新计算。父"一口气写完 8 个场景"反而是单条最长、缓存最连续的路径。

所以子 agent 买的不是 token 效率，而是四样东西：**上下文隔离、输出预算、墙钟并行、独立视角**。默认不用；只在下面这张表命中的情形下用。

### 7.2 裁决表

| 情形 | 做法 | 理由 |
|---|---|---|
| 源文 ≤ ~15k token 且场景 ≤ ~6 个 | **父自己顺序写** | 子 agent 的固定成本（各自一遍系统提示与工具表前缀 + 一遍指令）大于隔离收益 |
| 单场景要写很长（> ~1.5k 字） | 用子 agent | 输出搬进子预算，父的上下文不涨 |
| 场景之间高度独立 | `workflow` fan-out（每批 ≤ 4） | 墙钟收益 + 进度面板 |
| 场景之间有强因果（后场景依赖前场景的用词/线索） | **串行，父自写，或"写完 A 再派 B"** | 一致性 > 并行 |
| 一本模组产出多种派生物（场景 + NPC） | 按各自窗口派子 agent，**不做二次汇总** | 见 §7.5 |
| 需要二次校验已写文件 | **不用子 agent** | 用 `lint_notes.py`：确定性、零 token、秒级 |

### 7.3 必须禁止的三种缓存浪费

1. **子 agent 自己 `skill` 加载技能** → 技能正文会落在子 agent 的第一次工具结果里，各子 agent 各不相同、无法互相复用，等于每个场景白付一次规范（约 2~3k token）。
   *正确做法*：**父读规范，转述进子 agent 的 prompt 固定块。*
2. **每个子 agent 自己读整份 `source.txt`** → N 个场景 = N 份原文。这是最大的坑。
   *正确做法*：父只给**行号窗口**；窗口小则把文本**内联**进 prompt 尾巴。
3. **父在会话中途改动工具表或提示段** → 从改动点起父的缓存全废，子 agent 前缀也不再等于父前缀。
   *正确做法*：所有工具与提示段在会话开始时定好；中途不注册动态工具、不追加提示段。

### 7.4 子 agent prompt 的固定结构（前缀对齐）

```
<固定块>  角色声明 + 格式硬规范（§5.2~5.5）+ 文风要点 + 输出与禁止项
          ← 所有子 agent 逐字节相同，可复用前缀缓存
<可变块>  场景名/序号 + 该场景源文窗口（或行号指令）+ 出场 NPC 标准名 + 目标文件绝对路径
          ← 唯一的新增未缓存输入，放最后
```

要点：**不是"整条 prompt 都缓存"，最后一段必然重新计算**。规则就是"固定的在前、变化的在后"。

### 7.5 NPC 笔记：不做二次汇总

直觉做法（先写场景 → 父汇总 → 再派子 agent 写 NPC 问答）会**信息蒸发**：子 agent 看不到原文，只能凭场景笔记转述，"同一 NPC 在不同场景的态度差异""玩家可能问的意外问题"最先丢失。

正确做法：**NPC 子 agent 直接读该 NPC 出场的所有行号窗口**（从 `outline.md` 取并集）。它不需要先有场景笔记；"按场景分组的问答"这一结构由它按窗口顺序自己组织。

### 7.6 其他纪律

- 子 agent 指令里**明确禁止委托孙 agent**（`maxDepth` 默认 3）；fan-out 数量与批次由父负责。
- 子 agent **只允许 write 自己那一个目标文件**；已存在文件默认跳过并报告。
- v1 先用远端子 agent 跑通；确有成本压力时再考虑给 `tool-subagent` 开 `modelSelectionSettings: true`，把批量场景切到本地 MLX 路由（切换路由会使该子 agent 前缀与父不一致，需实测收益）。

## 8. 脚本规格

### 8.1 `extract_module.py`（只依赖标准库 + 可选 pypdf）

```
用法: python3 extract_module.py --src <文件> --out <source.txt> [--venv <路径>] [--json]

输出 source.txt:
  # 源: /abs/path/快乐王子.pdf
  # 页数: 42   抽取器: pypdf 4.x   质量: 0.98 (可打印字符比)   CJK比: 0.71   可疑字符: 0
  [[p1]]
  <第一页文本>
  [[p2]]
  ...
```

- **格式分派**：`.txt/.md` → 转码（BOM/UTF-16/GBK 探测）；`.docx/.doc/.rtf/.html/.htm/.odt` → `/usr/bin/textutil -convert txt -stdout`；`.pdf` → 先试 pypdf，若导入失败则**打印一条明确提示**（如何建 `.meta/.venv`、`pip install --no-cache-dir pypdf`）；`.epub` → 作为 zip 解包读取 XHTML 后剥标签。
- **质量自检**：可打印字符比例、(CJK 比例)、替换字符 `\uFFFD` 与私用区字符计数、连续重复字符比；低于阈值时输出 `QUALITY_WARN` / `QUALITY_FAIL` 并给出原因（典型：扫描版 PDF 无文字层）。
- **退出码**：`0` 正常；`2` 需要安装依赖（附命令）；`3` 质量不达标（父必须标"待人工确认"而不是编内容）。
- **绝不修改源文件**（只读打开）。

### 8.2 `lint_notes.py`（只依赖标准库）

```
用法: python3 lint_notes.py --module <模组名> [--root <仓库>] --out <lint-report.txt> [--json]
```

检查项与严重级：

| # | 检查 | 级别 |
|---|---|---|
| L1 | frontmatter 存在且可解析（Python 无 yaml 时用**受限解析器**：缩进块序列 + 单层键值） | FATAL |
| L2 | 场景 `tags` 恰好四项、顺序正确、`#<模组名>` 与目录名 slug 一致 | FATAL |
| L3 | 场景属性顺序为 `tags/date/地点/天气/人物`（缺失的属性跳过比较） | WARN |
| L4 | callout 语法：`^> ?\[!(success\|fail\|tip)\] +标题`；**必须带空格**；标题含"成功/失败"（`tip` 除外） | FATAL（缺空格/非法类型）/ WARN（标题缺字样） |
| L5 | `[!fail]` 与 `[!success]` 成对出现的比例（> 90% 成对 → 提示"失败块疑似滥用"） | WARN |
| L6 | `人物` 的每个 `[[…]]` 有对应 NPC 笔记 | FATAL（死链） |
| L7 | `地点` 非空；正文不含 `# 一级标题` | WARN |
| L8 | NPC 笔记：frontmatter 只有 `tags`，四项顺序正确 | FATAL |
| L9 | NPC 正文以 `- **身份**：` 与 `- **外貌**：` 开头 | WARN |
| L10 | 覆盖检查：`outline.md` 列的场景/NPC 是否都有文件 | FATAL |
| L11 | `素材/`、`调查员/` 只含 `_README.md`（无越界写入） | WARN |
| L12 | 原始模组文件存在且**未被改动**（mtime/大小与 manifest 记录一致） | WARN |

输出格式（父只需读 FATAL 行）：

```
FATAL 场景/德莱尼子爵府.md:75  callout 缺少空格: >[!success] 估价成功
WARN  场景/后院.md:1          属性顺序异常: 天气 出现在 人物 之后
SUMMARY files=13 fatal=1 warn=1 checked=13
```

### 8.3 关于 `standalone tools`

**不新增模型工具脚本**（不写 `create_notes.py` 之类）：目录骨架与逐文件写入用 `write` 工具就够，多一个生成脚本只会多一处需要维护的规范副本。脚本只做两件模型做不好或做不稳的事：**二进制→文本**、**机械校验**。

## 9. 运行流程（端到端）

```
① 澄清（父 ↔ 用户）
   模组文件确切路径、模组语言、必要专名读法            [≤2 轮，能推断就不问]

   确认工作目录可写 → 模组文件就位仓库根 → 建 <模组名>/ 骨架 → 写 manifest 初稿

   extract_module.py → .meta/source.txt（含质量指标）
   质量不达标 → 停手报告

④ 大纲（父，读骨架层）
   .meta/outline.md（场景清单 + 行号窗口 + 出场 NPC）
   .meta/glossary.md（专名唯一写法）

⑤ 场景（父自写 / 子 agent / workflow）
   每个场景一个文件；固定块+可变块结构；子 agent 只回状态行

⑥ NPC（每 NPC 一个子 agent，读其出场窗口并集）
   每个 NPC 一个文件；同样只回状态行

⑦ 校对（脚本）
   lint_notes.py → lint-report.txt → 父只针对报错行定点 edit

⑧ 收尾（父）
   总览.md + manifest.md 更新 + 汇报（已完成 / 跳过 / 待人工确认）
```

## 10. 边界与失败模式

| # | 情形 | 处理 |
|---|---|---|
| E1 | 工作目录不可写 | 第 0 步即停手，给两种解法；子 agent 越界只会被自动拒绝，不许重试 |
| E2 | 扫描版 PDF / 无文字层 | `extract_module.py` 返回 `QUALITY_FAIL`；父标注 `待人工确认`，**不编造**；提示用户可用 OCR 或提供文字版 |
| E3 | PDF 依赖缺失且离线 | 脚本返回退出码 2 并打印手动安装命令；父转告用户，不静默降级成"凭封面猜" |
| E4 | 模组超长（> ~200k token 源文） | 先报告规模与预计批次，取得用户同意后再开工；进度写 manifest，支持断点续跑 |
| E5 | 用户已手改过笔记 | 重跑默认**只补缺**（不存在的场景/NPC）+ lint 报告；覆盖需用户显式指令 |
| E6 | 场景切分歧义（一个房间多个功能） | 拆成 `###` 而不是新文件；判据写进 `pipeline.md` |
| E7 | 同一 NPC 跨多场景 | 一份 NPC 笔记，问答按场景分组（不做多文件） |
| E8 | 文件名/标签含非法字符 | slug 化规则（§5.2）；文件夹名保留原文，只有 tag 与链接目标做规范化 |
| E9 | 模组语言非中文 | **笔记语言跟随模组语言**；`SKILL.md` 与 persona 的中文规则框架不变 |
| E10 | 用户提供的路径指向上传附件（`~/.dsh/attachments/…`） | 先复制进仓库根（只读复制），原文件不动；manifest 记录来源路径 |
| E11 | lint 报死链 | 父只改链接行，不重建文件 |
| E12 | 子 agent 写出的文件不符合规范 | lint 兜住；若同一子 agent 反复出错，父改为自写该场景并在 manifest 记录 |
| E13 | 需要后台跑长抽取（`run_in_background`） | 本 preset 未挂 `tool-jobs`，该参数不可用；改为前台执行并给足 `timeoutMs`。确实需要后台任务时，把 `tool-jobs` 行加回组合（宿主有注册表，加一行即可） |

### 13.0 第二轮修订：文学性成为一等要求（真实模组试跑后）

**触发**：守秘人在真实模组（`谁是恋母癖V1.1`）上试跑，结构全对、文笔全无 —— 场景笔记 224~849 汉字，
客厅写成家具清单，KP 无法朗读。

**根因**：本文档与技能把"具体、简洁"当成了终点（§6.2 的"宁可短而具体"、§6.3 的"一个空间 2~5 段"），
而「把大纲拓展成生动描写」这一真正的目标从未被写成**可判定**的要求。

**架构层面的修订**：

1. 新增 `references/literary-standard.md` 作为**文风的唯一标尺**，含及格线数值
   （场景 ≥1200 汉字 / ≥4 叙述段；NPC ≥900 汉字）与五步拓展公式；
2. §6.2 SKILL.md 顶部加"笔记要被朗读"门禁，步骤 6 对篇幅 WARN 要求整段重写；
3. §8.2 lint 增加两条检查：**正文长度地板**（场景 700 / NPC 500 汉字）与
   **叙述段落密度**（各 ≥3 段），并输出每篇字数统计表 —— 让"薄"变成可观测信号；
4. §7.1 路由纪律写明：**子 agent 默认必须与父同模型**，不得为省钱把正文写作切到弱模型；
5. §7.2 增加父对子 agent 的拒收标准。

修订只落在技能包与 lint 脚本，**组合（§4）与脚本接口未变**，因此不需要重新挂载校验。
